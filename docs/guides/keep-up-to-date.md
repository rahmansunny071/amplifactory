# Keep up to date

A project that uses amplifactory gets new releases through the **`sync-root-factory`** skill, and sends factory
problems back through the **`factory-lesson`** skill. Both run in Claude Code inside the project. Releases and
lessons are described from the template's side in [Evolving the template](evolving-the-template.md).

## Update a generated repo

A repo generated by Copier records its version in `.copier-answers.yml`. Run `uvx copier update` yourself, or, in
Claude Code inside the repo, say:

> sync the factory to the latest release

The skill opens a PR for you to merge. Before it runs `copier update`, `sync.py copier-check <tag>` confirms the tag
is annotated, `_commit` is a release tag and `_src_path` is the GitHub template (not a local clone). Copier does a
three-way merge and marks conflicts; the skill resolves the mechanical ones, lists the rest for you, and never merges.

!!! note "Renamed from agent-factory"
    The template was renamed to `amplifactory`. A repo whose `.copier-answers.yml` still says
    `_src_path: gh:rahmansunny071/agent-factory` keeps working (GitHub redirects the old URL and
    `copier-check` accepts both names). Updating that line to `gh:rahmansunny071/amplifactory` is optional.

## Update a repo that only carries the skill

A repo that adopted just the `factory/` skill (see [Adopt in an existing repo](adopt-in-existing-repo.md)) is
**shadowing**: it has no `.copier-answers.yml`, so the skill applies the release by replacing the skill folders
from the tag.

`.claude/skills/factory/VERSION` (written by the sync, and shipped from the first release that has it) records
which release the copy came from. Then, in Claude Code in the repo:

> sync the factory to the latest release

The `sync-root-factory` skill:

- works on a new branch `local/adopt-<tag>` cut from a fresh `origin/<default branch>`, and refuses a dirty tree;
- replaces **every skill folder the tag ships** (`factory/`, `factory-lesson/`, `sync-root-factory/` and any future
  one) byte for byte from the **tag**. A folder the old tag had is replaced only after it matches the version the
  repo claims; a new one is added; a folder the old tag did not have but you already have (your own skill, or a
  hand copy) is refused, never overwritten; your own other skills are never touched;
- turns the CHANGELOG entries since your version into a checklist; it edits `CLAUDE.md`, `.claude/commands/*`,
  `README.md` and `CHANGELOG.md` for the ports it can do safely, never sets a policy value (the `Real data:`
  level, the release phase), creates only the labels that are missing, and lists everything else under "Open";
- opens a PR with a Handoff and never merges it.

**Every sync, the first included:** run the **target tag's** `sync.py`, extracted outside the repo, never the copy in
the repo (which may predate the guards, and does not exist yet the first time). Nothing is committed before the
adopt branch exists, so this works on a protected `main`:

```bash
R=$(git rev-parse --show-toplevel); URL=https://github.com/rahmansunny071/amplifactory.git; TAG=vX.Y.Z  # latest release
T=$(mktemp -d)                                  # outside the repo
git init -q --bare "$T/src"
git -C "$T/src" fetch -q --depth 1 "$URL" "refs/tags/${TAG}:refs/tags/${TAG}"
git -C "$T/src" cat-file -t "refs/tags/$TAG"    # must print: tag  (annotated)
mkdir "$T/x" && git -C "$T/src" archive "$TAG" template/.claude/skills/sync-root-factory | tar -x -C "$T/x"
python3 -I "$T/x/template/.claude/skills/sync-root-factory/scripts/sync.py" --repo "$R" status
# first sync only, while factory/VERSION is missing: add --assume-tag <tag the folder was copied from>
```

`--assume-tag` is needed only while `factory/VERSION` is missing (the first sync): it stands in for the file, and
the folder is still checked against that tag. Later syncs leave it out; `sync.py` refuses one that disagrees with `VERSION`. Then ask Claude to sync; the skill runs the same extracted script.
The old way (copy `sync-root-factory/` into the repo and commit it) is no longer needed: the adopt branch is cut
from `origin/<default>`, which would not contain that commit. If you already committed one and the old tag did not ship it (before v0.8.0), `apply` refuses it; on `local/adopt-<tag>` run `git rm -r .claude/skills/sync-root-factory`, commit, and
rerun.

**If the check fails** (your copy matches no tag, for example because a `main`-only commit was layered on a tag):
the sync stops and lists the differing files. There is no override. If the edits are unwanted, restore the copy of the
**recorded** tag, the one `verify-local` compared against (the version in `factory/VERSION`, or your `--assume-tag`; not
the target tag, whose `VERSION` would make the repo look synced). Do it on `local/adopt-<target tag>`, because a commit
on local `main` is not on the adopt branch:

```bash
OLD=v0.7.0                                      # the recorded tag
git init -q --bare "$T/old"
git -C "$T/old" fetch -q --depth 1 "$URL" "refs/tags/${OLD}:refs/tags/${OLD}"
test "$(git -C "$T/old" cat-file -t "refs/tags/$OLD")" = tag || { echo "not annotated: stop"; false; }
rm -rf "$R/.claude/skills/factory"
git -C "$T/old" archive "$OLD" template/.claude/skills/factory | tar -x --strip-components=2 -C "$R/.claude/"
git -C "$R" add -A .claude/skills/factory && git -C "$R" commit -m "restore factory/ to $OLD"
```

then rerun the sync. If the edits are wanted, port them after the sync.

## File a factory problem upstream

A **factory problem** (not a bug in the project's own code) found while driving a project is filed in amplifactory
as an issue labelled **`lesson`**:

- what happened, with links;
- the fix applied in the project, if any;
- the template files to change.

File it **when it happens**, not at the end of the run.

In a generated repo, ask Claude Code to "file a factory lesson: ..." and the **`factory-lesson` skill** does it:

1. finds the template repo from `.copier-answers.yml` (`_src_path`), used only when it is a GitHub source (`gh:`, `https://github.com/`, `ssh://git@github.com/`, `git@github.com:`); a local path, an empty value or a missing file falls back to `rahmansunny071/amplifactory`; the old slug `rahmansunny071/agent-factory` (any case) is mapped to the new one; it then confirms the slug with `gh repo view`; it never files in the current repo;
2. searches open and closed `lesson` issues for a duplicate: an open match gets a comment instead of a new issue; a closed match means it is already fixed, so it points to the release that fixed it and to updating (`copier update`, or the `sync-root-factory` skill);
3. drafts the body (What happened, Fix applied in the generated repo, Template files to change, Options, Takeaway) and checks it for real data values, secrets and private paths, since the issue goes to another repo;
4. asks you **once** (if you edit the draft, it re-checks the edited text for real data and shows the result before filing), then creates it with the `lesson` label and reports the URL;
5. offers a comment on the downstream PR or issue linking the lesson, only if you agree.

It needs a `gh` login with access to the template repo (private repos need one).
