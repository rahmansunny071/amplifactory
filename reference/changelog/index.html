    Changelog¶

    • v0.7.0 (2026-11-25): Real-data access is a per-repo choice (#33, from pensieve-traces, which allows reading real data shapes), plus ready-to-merge follow-ups (#35).
    • The skill no longer hard-codes "agents may not read real user data".
    • Question: real_data_access (never, with-approval, allowed; default never, so copier update changes behaviour for no one). It renders a ## Real data section in CLAUDE.md whose first line is Real data: <level>..
    • Always on: never commit real data; never quote values from it (field names, counts and shapes only); tests use synthetic fixtures only; read data where it lives and never copy it into the repo or worktree; a stricter hard rule overrides the level.
    • with-approval: the maintainer approves one named source on the issue or PR, for that issue or PR only. Standing access means allowed.
    • Skill: "Reality check" reads the line from CLAUDE.md on main. A missing or unrecognised line means never. Briefs carry the rule to every subagent; reviewers tag real-data values in the diff or text as a blocker.
    • Repos that adopted the skill by hand (such as pensieve-traces) must add a Real data: <level>. line, or run copier update --data real_data_access=<level>; until then they read as never.
    • Template CI renders with-approval and allowed and guards the rendered text.
    • Ready-to-merge follow-ups (#35). The opt-in rule's docs say it matches only commands ending in --delete-branch. queue.py --json adds waiting_to_merge ([{"issue", "pr"}]) and the table lists a loose merge issue once. The skill names the stale-label check (gh issue list --state closed --label factory:ready-to-merge). docs/reference/scripts.md says issues, not PRs, carry the label.
    • v0.6.0 (2026-11-25): Two lessons from pensieve-traces. Docs ship with the code (#30), whose README still called a built feature "planned", and a ready-to-merge hand-off (#32), because Claude Code's auto mode refused the skill's --admin merge.
    • Docs ship with the code (#30).
    • Hard rule in CLAUDE.md, replacing "every user-visible change updates README.md and CHANGELOG.md": every code change ships its docs in the same PR, both new docs and updates to any README, CHANGELOG, docstring or .factory/designs/ text it makes wrong or stale. Docs that disagree with the PR's code break a hard rule, so they're a blocker even in mvp. Mismatches outside the PR's diff are filed, not fixed.
    • Documentation tech-debt issue: one open issue titled exactly "Documentation tech-debt" (documentation, P2) whose native sub-issues (documentation, improvement, P2) are the doc todos. bootstrap.sh creates it and the documentation label; the skill finds it by title and creates it if missing, so existing repos need no re-bootstrap. New lanes.py doc-debt find|add|list. queue.py never lists the tracking issue as work.
    • Skill: the builder updates the docs its change affects and adds a Docs line to the Handoff (docs updated, or "none needed" and why). The code reviewer checks docs against code in the changed area: a mismatch the PR causes is a blocker, an older one is the new doc-debt tag. The orchestrator files doc-debt findings as sub-issues of the tracking issue (not in the PR's improvement issue) and resolves their threads with the link. Ride-alongs: the builder gets the open doc todos and fixes those about files its PR already touches (Closes #N). Documentation todos from planning also go under the tracking issue.
    • New merge gate 12, "Docs ship with the code": the Handoff's Docs line is present, and a diff that changes code but no docs states a reason that holds up. "You aren't unsure" is now gate 13.
    • The issue format's "Docs updated" criterion names the specific docs, and there's a format for doc todos. The Actions-path build-from-design (a "## Docs" PR section) and review-against-design (a "Docs vs code" check) follow the same rule.
    • Fixed along the way: SKILL.md said "Three principles" above four.
    • Ready-to-merge hand-off (#32). When every gate passes but the merge is refused (the harness denies gh pr merge, or GitHub rejects it), that is no longer a dead end.
    • Skill: step 8 tries the merge; if it is refused, the skill never works around it (no gh api, other flags or other tools). It labels the PR and issue factory:ready-to-merge, posts one PR comment with the exact merge command and the gate summary, removes the in-progress label and moves on, like flag-and-continue. The end-of-run report lists these PRs so you can merge in one batch.
    • Merge command: plain gh pr merge <PR> --merge --delete-branch when mergeStateStatus is CLEAN; --admin only when the PR is blocked solely by the required review. Gate 2 no longer presents --admin as the only path.
    • queue.py: new state merge (uses no slot; the lane's later issues wait) and a "Waiting for you to merge" list. bootstrap.sh creates the factory:ready-to-merge label.
    • Opt-in: the generated README and the docs explain how to add a Claude Code permission rule for gh pr merge * --merge --admin --delete-branch so the skill can merge itself. The template ships no such rule, and the ruleset is unchanged.
    • Template CI guards check the new label, state, hand-off text and opt-in docs.
    • runlog.py status shows an issue whose last step is ready-to-merge as waiting on the maintainer, not in flight (#36).
    • v0.5.1 (2026-11-24): Data-loss blocker (#27). Reviewers now treat this as a blocker, not an improvement: irreversible loss or overwrite of the user's existing data (source files, history, remote repos) on a plausible invocation, even a mistaken one, when a cheap guard would prevent it. The design reviewer asks plans that write, move or delete files to name their overwrite rules. Updated in the Code and Design reviewer briefs, the review command, CLAUDE.md, the README and the pipeline docs.
    • v0.5.0 (2026-11-24): Swim lanes (#23). Work is organised as prioritized lanes of ordered, dependency-linked issues.
    • Lanes: a parent issue labelled lane whose native GitHub sub-issues are processed one at a time, in order. Priorities P0–P3 on lanes and issues. Dependencies between issues or whole lanes use native "blocked by" links, with the body's "Depends on #N" line kept as a fallback.
    • Brainstorm is two-level: lanes (priorities, lane dependencies, main path), then ordered issues per lane, with rolling-wave detail (only the next one or two issues fully written). One confirmation creates everything.
    • Scheduling: queue.py is lane-aware. Each lane's current issue and state, lanes ranked by priority, "Work now" for --lanes N. One lane at a time by default; the skill asks the maintainer before running more lanes in parallel. A question on a lane pauses only that lane. A collision guard holds a second lane whose plan touches the same files.
    • New scripts/lanes.py (sub-add, order, block, priority, project-add, show) wraps the GitHub sub-issue, dependency and Projects calls.
    • bootstrap.sh creates the lane and P0–P3 labels and a GitHub Project board with a Priority field (needs the project scope).
    • First real test: pensieve-traces restructured into four lanes.
    • v0.4.0 (2026-11-24): Flag and continue (#21). The skill never blocks the session waiting for the maintainer.
    • Questions (a reviewer's [question], a design reviewer's ASK, gate failures, unverifiable data assumptions, persistent blockers) are posted as inline, line-anchored PR review comments with options and a recommendation. The issue and PR get factory:needs-maintainer, and the run moves on to independent work. An in-session question only when nothing else can proceed.
    • Resume ("resume the factory") works from GitHub state: queue.py shows which waiting PRs have new maintainer replies. Answers are applied by Opus directly for small edits, or by a Sonnet resume builder otherwise. Then an Opus check scoped to those threads, then the gates. @claude on the PR (Actions factory-chat) also works.
    • Builder handoffs: the builder keeps a "## Handoff" section in the PR body after every phase. Replacement agents and reviewers start from it. At merge, its gist goes into .factory/designs/issue-N.md as "Implementation notes".
    • Where knowledge lives: GitHub and the repo are the source of truth; the run log is a local cache and cost ledger that only points at them; Claude's memory holds preferences. New CLAUDE.md section.
    • Gates: new "Handoff present" and "all review threads resolved". bootstrap.sh turns on "require conversation resolution" and creates the factory:needs-maintainer label. gates.md documents the API calls for posting inline questions and for finding and resolving threads.
    • The plan phase now opens a draft PR, so plan-level questions can be anchored to lines.
    • runlog.py schema v2: actor, refs (commit, thread ids), steps needs-maintainer, resume, handoff-written; cost by role. queue.py: needs-maintainer state, with replied first.
    • v0.3.1 (2026-11-24): Fix: the skill now works on local/issue-N branches, so the GitHub Actions factory-review (which watches factory/issue-*) no longer duplicates the skill's own Opus review on every push. The per-run "disable the Actions review?" question is removed, and template CI checks both. Fix: bootstrap.sh now creates the improvement label that the v0.3.0 skill depends on (template CI checks it). Docs: the README is rewritten for the skill-first workflow: both ways to run the factory (the factory skill and GitHub Actions), how the skill keeps cost down, the release_phase question, the skill and run-log files, using the skill in a repo not generated from the template, and how the template evolves (lessons → releases → copier update).
    • v0.3.0 (2026-11-24): A faster, cheaper factory skill, from running pensieve-traces #2 and #3 (about 1.4M subagent tokens for two issues).
    • Urgency triage (#17): a release_phase question (mvp by default) writes a "Release phase" section into CLAUDE.md. In mvp, reviewers tag findings blocker or improvement; only blockers are fixed in-PR; the orchestrator files one batched improvement issue per PR, and main-path issues never depend on improvements. queue.py lists ready main-path issues before ready improvements.
    • 2 subagents per issue instead of 10–15: one Sonnet builder plans (phase 1), builds (phase 2) and fixes blockers, each step a SendMessage to the same agent, so it never re-reads context (#14). One fresh Opus code reviewer runs in parallel with CI. Blocker fixes are verified by CI plus the orchestrator's repro, with no re-review. Risk tiers: only critical issues (privacy/security, new dependencies, shared data contracts) get a separate Opus design review. Standard issues get an orchestrator plan skim.
    • Run log (#14): scripts/runlog.py (add, status, summary) writes .factory/runs/*.jsonl (gitignored). Sessions resume an in-flight issue, and the end-of-run summary reports wall time, fix rounds and tokens by model. The skill suggests a fresh session after 2–3 issues.
    • Overlap (#15): plan an independent ready issue while another builds; at most two in flight; merges one at a time, updating the other branch with main afterwards.
    • Reality check (#13): never build on an unverifiable assumption about real data; ask the maintainer, ideally with a local shape-only script. The issue format records what was verified against real data, plus the risk tier.
    • Bounded CI waits: watch the workflow run (gh run watch <id>), not PR checks; no sleep loops. Rerun to clear a stale pending check.
    • Template CI checks all of the above, including the runlog.py self-test.
    • v0.2.0 (2026-11-24): factory skill: run the factory from a Claude Code session instead of label by label.
    • Brainstorm mode: Opus brainstorms with the maintainer, proposes an issue breakdown, gets one confirmation, Sonnet subagents draft Factory-task issues and Opus checks and creates them with dependency links.
    • Run mode: for each ready issue (scripts/queue.py, dependency-ordered), Sonnet designs → an Opus subagent reviews the design → Sonnet builds in a worktree → CI → a fresh Opus subagent reviews the code → Opus auto-merges (--merge --admin) when every gate in references/gates.md passes.
    • Stops and asks when unsure, on failed gates, or on workflow, dependency, version or CLAUDE.md changes. Never adds the Actions trigger labels, so the two modes don't duplicate work.
    • Template CI checks the skill files and runs queue.py --self-test.
    • Hardened by its first real run (pensieve-traces #2, #3), lessons #10, #11, #12 and #16: reviewers don't add unverifiable scope (it becomes a question); stop when two rounds find defects in the same area; narrow "Design final check" and "Code re-review" briefs; non-blocking notes and (optional) items (optional items are filed as linked follow-up issues); a Reviewer-notes slot in the Builder brief; repo slug taken from gh, not memory; a rule for installing outside packages; asks whether to disable the weaker Actions review for the run; design length cap by size (S ~400, M ~800 words); design-issue handles local-mode labels.
    • v0.1.1 (2026-11-24): Fixes from driving the first generated factory (pensieve-traces) end to end.
    • Build and chat agents can run checks on PRs authored by claude[bot] (restrict_untrusted_prs: "false"), protected by a new build step that refuses design branches touching anything outside .factory/designs/ (#3).
    • The review agent runs on implementation PRs opened by claude[bot] (allowed_bots: "claude") (#5), and verifies "Checks run" against CI with gh pr checks instead of trying to run code (#6).
    • The build agent reports denied or missing commands on the design PR with factory:blocked, never a silent exit (#3).
    • Docs: a "Changing the factory itself" section in the generated README. It covers workflow changes in their own PR (#7), updating open factory PRs after a workflow change (#4), merging your own PRs, and treating "green but no artifact" as a failure. CLAUDE.md and the build prompt say the same.
    • Template CI asserts every guardrail above is present in the rendered project.
    • v0.1.0 (2026-11-24): First release as a Copier template, generalized from pensieve-traces. Factory workflows, agent commands, issue template, CI, package skeleton, scripts/bootstrap.sh (labels, main ruleset, fork-PR approval), and a template CI that renders three variants and runs their checks.
